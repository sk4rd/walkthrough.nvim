This file is the reference. The README gives a first walk-through. The agent
side has its own short copy of the protocol in
`skills/walkthrough/references/format.md`. A test (`tests/docs_spec.lua`)
checks that both documents name every field, verdict, evidence value, thread
state and inbox item kind that the code has, and that this file names every
command, option, key, mapping and public function.

==============================================================================
1. CONCEPTS                                             *walkthrough-concepts*

walkthrough.nvim lets you annotate an agent's plan, its change, or any code
inside Neovim. The agent session you work with (the "working session") answers
and proposes next to the line you wrote on. Approved work becomes small
commits that stand on their own.

map          The ordered list of commits of a change. Each commit lists its
             files, with one sentence for each. It is shown in the panel
             (|walkthrough-map|).
commit       In the map: a coherent set of lines, maybe from several files and
             maybe only part of a file, that builds on its own. Commits are
             ordered so that nothing depends on a later one. Not the same as a
             git commit: it becomes one when you commit it. In the protocol it
             is a `group` (|walkthrough-format|).
entry        One file of a commit, with its sentence (`title`). In the
             protocol it is a `step`.
thread       Something written on lines, with the replies under it. There are
             two kinds, both yours: a question (`question`) and a change
             request (`change`). See |walkthrough-threads|.
finding      A remark of the agent on a line, with a verdict (keep, simplify,
             remove, moved) and how it knows (ran, read, opinion). In the
             protocol it is a note. See |walkthrough-findings|.
proposal     The agent's answer to a change request, or a finding that says
             what to do. You accept or decline it; only then the agent edits.
compact view The changed parts of the current commit in one scrolling buffer.
file view    The real file, editable, with the diff drawn over it.
             (|walkthrough-views|)
working session
             The agent session next to Neovim. It receives your messages
             through the sender (|walkthrough-senders|). If it is busy, the
             message waits in its queue and the thread shows "waiting".

Three rules hold everywhere:

  - The agent never stages, commits or edits on its own. Edits follow an
    accepted proposal. A commit follows your confirmation.
  - Threads of a change are gone after its commit. Nothing is kept as a log.
  - Nothing opens on its own. You start a review, and you ask for the map.

The agent talks to Neovim over its server socket, with |--remote-expr|:

>
    nvim --server $NVIM --remote-expr \
      "v:lua.require'walkthrough'.load('/tmp/commit.json')"
<

|v:lua| calls a Lua function from an expression. The script
`skills/walkthrough/tour.sh` finds the socket and does this for you. It uses
`$WALKTHROUGH_NVIM`, else `$NVIM` (Neovim sets it inside its terminal
buffers), else the only `nvim.*.0` socket in `$XDG_RUNTIME_DIR`.

The plugin defines the command `:Walkthrough` and the |<Plug>| mappings. It
defines no global key unless you pass `keys` to setup().

Requirements: Neovim 0.10 or newer, and `git`
(https://git-scm.com/docs/git). Staging, reject and the staged counter need
https://github.com/lewis6991/gitsigns.nvim . `:checkhealth walkthrough`
(|:checkhealth|) reports what is missing.

2. THE THREE SCENARIOS                                 *walkthrough-scenarios*

In the keys below, P is the prefix (`<leader>w` with `keys = true`,
|walkthrough-mappings|).

A. Review a finished change                           *walkthrough-scenario-a*

  1. Start with `Pr` (`:Walkthrough review`). Neovim lists the changed files
     from git at once (|walkthrough-review|). No agent is involved.
  2. Press `PM` (`:Walkthrough request`) to ask the working session for the
     map (|walkthrough-request|). It answers with the ordered commits, one
     sentence per file, every changed line assigned to a commit, and its
     findings.
  3. Read in the compact view. `]w` and `[w` move between entries, `P]` and
     `P[` between commits, `Pv` jumps to the same line in the real file and
     back. Lines of other commits are dimmed and labelled with their commit.
     Lines in no commit are flagged.
  4. Annotate, in either view. `Pa` asks a question: it is sent at once and the
     answer appears under the line. `Pc` writes a change request: it is
     collected, `Pm` sends all of them, and the agent replies to each with a
     proposal. `Py` accepts a proposal or finding, `Pd` declines it. `P-` and
     `P+` ask for a simpler or a deeper answer. `Pt` opens a long thread in
     full.
  5. Stage a commit with `Ps` (this file) or `PS` (every file). Exactly the
     commit's lines are staged, also in a file that holds lines of other
     commits (|walkthrough-stage|).
  6. Commit with `PC`. The project's check runs on exactly what is staged, the
     agent proposes a message, you edit or confirm, Neovim makes the commit
     (|walkthrough-commit|).
  7. The commit's threads are deleted and the next commit is current.

B. Ask about existing code                            *walkthrough-scenario-b*

With no review open, `Pa` works on any line of any saved file in a repository.
It starts a session silently: no map, no panel, only the thread under the
line. Threads survive a restart and are deleted when you close the session
with `Pq` (|walkthrough-other|).

C. Plan review                                        *walkthrough-scenario-c*

When the agent leaves plan mode, a hook hands the plan to Neovim and the agent
waits. The plan opens as a document in a tab of its own. You write questions
and change requests on its lines (`Pa`, `Pc`; both are collected, because the
agent is waiting). Then `A` approves the plan, or `F` sends your annotations
back as feedback. The agent revises the plan and shows it again in the same
tab, with its replies under your lines. Without a reachable Neovim the normal
prompt of the agent appears. Claude Code is supported first; the hook is the
only part specific to it (|walkthrough-plan|).

3. SETUP OPTIONS                                           *walkthrough-setup*

setup({opts}) is optional. It raises an error for an invalid `panel_side`,
`code_min_ratio`, `view`, `sender` or `submit`. Options survive loading the
module again.

>lua
    require('walkthrough').setup({
      panel_side = 'left',
      keys = true,
    })
<

  `panel_side`       "left" (default) or "right": the side of the code window
                     where the map panel opens. "left" suits an agent terminal
                     on the far left: [ agent | panel | code ].
  `panel_width`      Width of the panel in columns. Default 40.
  `panel_min_width`  The panel never shrinks below this to make room for the
                     code. Default 30.
  `code_min_ratio`   The code window keeps at least this share of the screen
                     (a number above 0 and below 1). Default 0.5. It is
                     applied again after each update, when a window opens or
                     is resized, and when the screen size changes. The space
                     comes from the panel first, down to `panel_min_width`,
                     then from the other windows.
  `max_removed_lines`
                     Deleted lines shown under one hunk in the file view
                     before "... N more removed lines". Default 10.
  `view`             "compact" (default) or "file": the view a review opens
                     in (|walkthrough-views|).
  `sender`           How messages reach the agent: "auto" (default),
                     "claudecode", "terminal", "clipboard", or a function.
                     See |walkthrough-senders|.
  `submit`           true (default): a message is delivered so that the agent
                     starts on it, and the focus stays where it is. false: it
                     is typed or pasted but not submitted, and the focus moves
                     to the agent. See |walkthrough-senders|.
  `terminal_pattern` Which terminal buffer is the agent, for the "terminal"
                     sender. A list of Lua patterns, one pattern, or a
                     function. See |walkthrough-senders|. Default: "claude",
                     "codex", "opencode", "gemini", "aider" and "amp" (as a
                     whole word).
  `state_dir`        Where the review state is saved, one file per
                     repository. Default: |stdpath()| "state" followed by
                     "/walkthrough". See |walkthrough-persistence|.
  `keys`             `true` maps the default keys under the prefix
                     `<leader>w`. A string maps them under that prefix.
                     `false` maps nothing. Only keys that are still free are
                     mapped. See |walkthrough-mappings|. Default `false`.

4. COMMANDS                                             *walkthrough-commands*

`:Walkthrough {subcommand} [argument]` is the only command. Subcommands
complete with <Tab>. An unknown one lists the valid names.

Start
  `:Walkthrough review [ref]` start a review without an agent: one entry per
                              changed file (|walkthrough-review|).
  `:Walkthrough request`      ask the working session for the map of the
                              change under review (|walkthrough-request|).
  `:Walkthrough resume`       bring back the saved review of this repository
                              (|walkthrough-persistence|).
  `:Walkthrough close`        end the session: remove all marks, close the
                              panel, forget the loaded commits. The commits of
                              a change stay saved (`resume` brings them back);
                              the threads on files no review lists are
                              deleted from the saved state.

Move
  `:Walkthrough next`         next entry.
  `:Walkthrough prev`         previous entry.
  `:Walkthrough note-next`    jump to the next thread or finding below the
                              cursor, in the file of the current window.
  `:Walkthrough note-prev`    jump to the previous one.
  `:Walkthrough group [x]`    switch between loaded commits. `x` is a commit's
                              subject, "next", "prev", or a number to move by
                              (it wraps). Without `x` it lists the loaded
                              commits. A commit shows the entry where you left
                              it.
  `:Walkthrough view [x]`     switch between the compact view and the file view
                              (|walkthrough-views|). `x` is "compact" or
                              "file"; without it the view is switched.
  `:Walkthrough map`          show the map panel, or hide it when it is open.
                              It changes nothing about the code window.
  `:Walkthrough back`         show the current entry again (use it after you
                              opened another file in the code window).

Write
  `:Walkthrough ask [text]`   ask a question about the cursor line, or the
                              lines of a range (`:'<,'>Walkthrough ask`). It
                              works on any saved file, in any window, with or
                              without a review (|walkthrough-other|). A thread
                              starts and the question is sent at once. If the
                              lines carry a thread of yours that is not done
                              or declined, the text is a reply in it,
                              whatever its kind. A finding on the line is sent
                              along. Without text it asks for it. If nothing
                              can be sent, the thread stays a draft and goes
                              out with `send`.
  `:Walkthrough change [text]`
                              the same for a change request: the thread is
                              collected, nothing is sent until `send`. The
                              agent answers with a proposal.
  `:Walkthrough send`         send everything not delivered yet, in all
                              commits of the repository, as one message:
                              change requests, collected replies, and
                              decisions that could not be sent.
  `:Walkthrough thread`       open the thread or finding on this line in full,
                              in a float (|walkthrough-thread|).
  `:Walkthrough thread-delete`
                              delete the thread on this line.
  `:Walkthrough explain {x}`  `x` is "simpler" or "deeper": ask the agent to
                              rewrite its last message in the thread under the
                              cursor, or the explanation (`detail`) of the
                              finding there, at that level. Elsewhere it only
                              says so. The level is remembered as `depth`
                              (|walkthrough-status|) for later answers.

Decide
  `:Walkthrough decide {x}`   `x` is "accept", "reject" or "clear": your stance
                              on what is under the cursor, in the code or in
                              the thread float: the proposal of a thread
                              (state "proposed") or the verdict of a finding.
                              It is sent at once; "clear" takes back a
                              decision the agent has not been told.

Approve
  `:Walkthrough stage`        stage the lines of the current commit in the
                              file of the current entry (|walkthrough-stage|).
                              An entry without `hunks` stages all unstaged
                              changes of its file.
  `:Walkthrough stage all`    the same in every file of the commit. It asks
                              first if some entries were not shown yet.
  `:Walkthrough reject`       discard the unstaged lines of the commit in the
                              current file, after a confirmation. Staged lines
                              stay. It cannot be undone.
  `:Walkthrough base`         open the file as it was before the change, in a
                              read-only float (|walkthrough-base|).
  `:Walkthrough commit`       check, message and commit what is staged
                              (|walkthrough-commit|).

Plan (|walkthrough-plan|)
  `:Walkthrough plan`         go to the tab of the plan that waits for your
                              decision, and open it again when you closed it.
                              With none it says so.
  `:Walkthrough plan approve` let the plan through: the agent goes on, the tab
                              closes, the plan is deleted. Annotations still
                              open are dropped (the notification counts them).
  `:Walkthrough plan feedback`
                              send your annotations of the plan back to the
                              agent in one message. With none it asks what
                              should change and sends that.

Help and session
  `:Walkthrough keys`         show the key cheat sheet (|walkthrough-mappings|).
  `:Walkthrough status`       one line, for example: `entry 1/3 of "Share the
                              LAN constants", seen 2, 2 commits loaded,
                              compact view, 1 stale`. It adds "map requested"
                              while the agent has not answered a request for
                              the map.
  `:Walkthrough discard`      delete the saved state of this repository and
                              clear the screen.
  `:Walkthrough reviewed [name]`
                              record the working tree as a snapshot
                              (|walkthrough-incremental|). It is no part of the
                              workflow and has no default key. The default
                              name is "reviewed". It notifies with the short
                              commit id.

5. MAPPINGS AND KEYS                                    *walkthrough-mappings*

Every action has a |<Plug>| mapping (normal mode; `ask` and `change` also in
visual mode, where they cover the selected lines):

  <Plug>(walkthrough-review)             review the uncommitted changes
  <Plug>(walkthrough-request)            ask the agent for the map
  <Plug>(walkthrough-resume)             bring back the saved review
  <Plug>(walkthrough-close)              end the session
  <Plug>(walkthrough-next)               next entry
  <Plug>(walkthrough-prev)               previous entry
  <Plug>(walkthrough-note-next)          next thread or finding
  <Plug>(walkthrough-note-prev)          previous thread or finding
  <Plug>(walkthrough-group-next)         next commit
  <Plug>(walkthrough-group-prev)         previous commit
  <Plug>(walkthrough-view)               switch compact view and file view
  <Plug>(walkthrough-map)                show or hide the map panel
  <Plug>(walkthrough-back)               back to the current entry
  <Plug>(walkthrough-ask)                ask a question here (sent at once)
  <Plug>(walkthrough-change)             write a change request here
  <Plug>(walkthrough-send)               send change requests and decisions
  <Plug>(walkthrough-thread)             open the thread or finding in full
  <Plug>(walkthrough-thread-delete)      delete the thread under the cursor
  <Plug>(walkthrough-simpler)            ask for a simpler answer
  <Plug>(walkthrough-deeper)             ask for a deeper answer
  <Plug>(walkthrough-accept)             accept the proposal or finding here
  <Plug>(walkthrough-decline)            decline it
  <Plug>(walkthrough-undecide)           clear a decision that is not sent
  <Plug>(walkthrough-stage)              stage the commit in this file
  <Plug>(walkthrough-stage-all)          stage the commit in every file
  <Plug>(walkthrough-reject)             discard the commit's unstaged lines
  <Plug>(walkthrough-base)               show the base version
  <Plug>(walkthrough-commit)             check, message and commit
  <Plug>(walkthrough-plan-approve)       approve the plan
  <Plug>(walkthrough-plan-feedback)      send the plan feedback
  <Plug>(walkthrough-keys)               show the key cheat sheet
  <Plug>(walkthrough-reviewed)           record a snapshot (no default key)

With `keys = true`, setup() maps the default keys under the prefix
`<leader>w`. With `keys = '<leader>r'` (any string) it uses that prefix. With
`keys = false` (the default) it maps nothing. A key is mapped only when it is
still free: a key that you or another plugin mapped is left alone, and
calling setup() again changes nothing. Each mapping has a description that
starts with "Walkthrough: ". If which-key.nvim is installed, the prefix is
registered as the group "walkthrough". Without `keys`, map the actions
yourself:

>lua
    vim.keymap.set('n', ']w', '<Plug>(walkthrough-next)')
<

Default keys. P is the prefix. `]w`, `[w`, `]n` and `[n` do not use it.

Start
  Pr          review the uncommitted changes
  PM          request: ask the agent for the map
  PR          resume
  Pq          close
Move
  ]w  [w      next / previous entry
  ]n  [n      next / previous thread or finding
  P]  P[      next / previous commit
  Pv          switch between the compact view and the file view
  Pp          show or hide the map panel
  Pw          back to the current entry
Write
  Pa          ask a question (normal and visual mode)
  Pc          write a change request (normal and visual mode)
  Pm          send
  Pt          open the thread here in full
  PX          delete the thread here
  P-          simpler
  P+  P=      deeper
Decide
  Py          accept the proposal or finding
  Pd          decline it
  P0          clear a decision that is not sent
Approve
  Ps          stage the commit's lines in this file
  PS          stage the commit's lines in every file
  Px          reject: discard the commit's unstaged lines (asks first)
  Pb          base view
  PC          commit: check, message and commit what is staged
Plan
  PA          approve the plan
  PF          send the plan feedback
Help
  P?          key cheat sheet

The cheat sheet (`:Walkthrough keys`, `P?`, `?` in the panel) is a float
that lists every action in these groups with the key mapped to it right now.
An action without a key is shown as its `:Walkthrough` command, so the sheet
works with `keys = false`. It ends with the keys of the panel. `q` and
<Esc> close it. Cheat-sheet texts and the groups come from `lua/walkthrough/
keys.lua`.

*walkthrough-panel-keys*
Keys in the map panel (local to its buffer, which cannot be changed, so single
keys are free):

  <CR>      open the entry under the cursor (its sentence too), also when it
            belongs to another commit. On a heading: that commit, where you
            left it.
  s         stage the commit in this file
  S         stage the commit in every file
  m         send collected change requests and decisions
  b         base view
  x         discard the commit's unstaged lines in this file
  ?         key cheat sheet

*walkthrough-thread*
`:Walkthrough thread` (`Pt`) opens the thread or finding on the cursor line in
a centered float, as plain text: a heading (`t1 · question · path:10-12 ·
state`), the code lines (12 at most), then every message with `You:` or
`Agent:` (a proposal is marked `Agent (proposal):`). For a finding: its number,
verdict, evidence, decision, text and `detail`. The float draws itself again
when its thread changes while it is open. Its keys:

  r         reply (asks for the text; a question is sent at once, a change
            request is collected)
  y  d      accept / decline the proposal or finding
  -  + =    simpler / deeper
  X         delete the thread, after asking (the default answer cancels).
            Findings cannot be deleted.
  q  <Esc>  close

*walkthrough-base*
`:Walkthrough base` (`Pb`) opens the file of the current entry (in the compact
view: of the entry under the cursor) as it was before the change, in a
read-only float on the line that matches the entry's focus or the cursor. The
base is the entry's `diff` ref, else HEAD. `q` and <Esc> close the float.

*walkthrough-request*
`:Walkthrough request` (`PM`) sends one message to the working session through
the sender, asking it to build the map of the change under review. The message
holds the repository root, the base (HEAD, or the ref of the review), the list
of changed files (those of the local review when there is one, else git's, as
`review` computes them), and what is expected: sort the changes into commits
that each stand on their own, ordered so that nothing depends on a later
commit; send one map per commit with `tour.sh`; list every changed line of
each file under a commit; add findings. With no review open, the local review
starts first. Until a map of the agent arrives (a commit with a `group`),
`inbox()` lists `{ "kind": "map", "root", "base", "files" }` and `status()` has
`"map": "requested"`. Closing the session or discarding the review ends the
request. A failure to send is a notification ("the agent was not asked for the
map"); nothing else changes.

*walkthrough-review*
`:Walkthrough review [ref]` (`Pr`) needs no agent. It looks at the repository
of the current file, else of the working directory, and makes one entry for
every file that differs from {ref} (default HEAD) in the working tree, in the
order of `git status`. Untracked files that are not ignored count; deleted
files are left out. An entry has `diff` true (the ref when one was given) and
no sentence or ranges. The entries form the local map, one commit without a
subject, flagged `auto` and saved with the others. The first file is shown.
With no changed file it only says so. A commit with a `group` that the agent
sends takes its place, and the threads you wrote go to the entry of the same
file (the others are dropped). A map without a `group` from the agent replaces
it as well. While one from the agent is loaded, `review` refuses.

Staging such an entry has no commit to cut the file by: it stages all unstaged
changes of the file with gitsigns' `stage_buffer`, and says `staged {file}`.
`stage all` does it for every entry without `hunks`.

6. THE TWO VIEWS                                           *walkthrough-views*

A commit is shown in one of two views, both in the code window. The option
`view` says which one a review opens in; each commit keeps the view you chose
while it is loaded.

The file view shows the real file of the entry, editable, with LSP, and the
diff drawn over it (|walkthrough-marks|).

The compact view shows one read-only buffer with only the changed parts of the
commit's files, in map order: a heading per entry (the path, a `·`, the
sentence, `(new file)` for a file that is not in the base), then its git hunks
with 3 lines of context, separated by `⋯`. A line is its number (the old one
for a removed line), a sign (` `, `+`, `-`) and the text:

>
    backup.sh  ·  the destination can be set from outside
       8   fi
      10 - dest=/tmp/backups
      10 + dest=${BACKUP_DIR:-/tmp/backups}
      11
<

The base is HEAD, or the `diff` ref of the entry. An untracked file is all
added, and a new file is cut after 200 lines. An entry with `hunks` shows the
git hunks that have a line of the current commit; lines of other commits are
dimmed and labelled, lines in no commit flagged, staged lines marked with a ✓,
as in the file view. Threads and findings are drawn under their lines. A
heading counts what the view does not show, as in `(2 threads elsewhere)` or
`(1 finding elsewhere)`; other notes in the heading are `(binary file)`, `(no
diff)`, `(no changes)` and `(no lines of this commit)`.

`:Walkthrough view` (`Pv`) switches. From the compact view the file opens at
the line under the cursor (a removed line goes to the line it is shown above);
from the file view the compact view opens on the same file and line, or the
nearest line it shows. `]w` and `[w` move between the headings; `<CR>` in the
map puts the cursor on the heading. `ask`, `change`, `decide`, `thread`,
`explain`, `thread-delete`, `]n` and `[n` work in the compact view: the cursor
line (or the selected lines, which must stay in one entry) is a line of the
entry's file, and a removed line, a heading or a `⋯` line is refused. `stage`,
`reject` and `base` act on the entry under the cursor. The buffer is built
again after a write, a stage, a patch or a thread change, with the cursor kept.
A commit with no changed line to show (and `Other files`) opens in the file
view, and says why.

==============================================================================
7. THE MAP PANEL                                             *walkthrough-map*

The panel is the map. It lists every loaded commit of the repository: a
heading with the commit's subject (`Changes` for the local review, which has
none), and under it one line per entry. An entry shows the file, relative to
the repository root, the lines of the commit that are staged as `x/y` (only
for an entry with `hunks` and a `diff` of `true`), and below it the sentence.
`>` marks the entry on screen and a dim ✓ the entries you have seen. The
active commit's heading is highlighted. The last line counts the threads of
the repository, such as `2 waiting · 1 proposal · 1 not sent` (parts that are
zero are left out). `Other files` comes last (|walkthrough-other|).

`:Walkthrough map` (`Pp`) shows or hides it. The panel's bar shows the commit's
subject, `staged x/y`, `seen a/b`, the panel keys (|walkthrough-panel-keys|)
and `? all keys`; it adds "unsaved changes: save to refresh" while the code
buffer is modified (in the compact view: while any file of the commit is).

==============================================================================
8. THREADS                                               *walkthrough-threads*

A thread is written on lines of a saved file, in either view, in any window.
It has an id (`t1`, `t2`, ...), unique in the repository and never reused.

Kinds:
  `question`   yours. Sent the moment you write it. The agent answers without
               changing code.
  `change`     your change request. Collected while you read; `send` delivers
               all of them. The agent replies with a proposal.

Writing again on lines that carry an open thread of yours replies in that
thread, whatever its kind. A closed thread (`done` or `declined`) takes no
reply: ask a new question on those lines.

States, and the label drawn after the id:
  `draft`      written, not delivered: a change request waiting for `send`, or
               a question that could not be sent. Label "(not sent)".
  `waiting`    delivered, no answer yet. Label "(waiting)".
  `answered`   the agent answered. No label.
  `proposed`   the agent answered with a proposal. Label "(proposal)".
  `accepted`   you accepted the proposal. Label "(accepted)".
  `declined`   you declined it. Label "(declined)". Closed.
  `done`       the agent reported the work. Label "(done)". Closed.

The look under the line (the same in the compact view and the file view):

>
    » t1 (waiting) you: why a set here?
      ↳ A set groups related values under one name. ...
<

The last message of the agent follows with `↳`. Done and declined threads are
dimmed. A thread is shortened to 6 lines; a longer one ends with `… full
thread: {key}`, and `Pt` opens it. `(code changed)` after the text means the
code on those lines was rewritten after the thread was started.

`:Walkthrough thread-delete` (`PX`) deletes the thread under the cursor. Threads
of a change are deleted after its commit.

==============================================================================
9. FINDINGS AND DECISIONS                               *walkthrough-findings*

A finding is a note of the agent on a line: a few words (`text`), a longer
explanation (`detail`, shown dimmed under it, 6 lines at most), a verdict and
the evidence. It is drawn with a number badge, the verdict (KEEP, SIMPLIFY,
REMOVE, DONE, MOVED), your decision if you made one, and the evidence word.

*walkthrough-verdicts*
Verdicts:
  `keep`      the code is fine as it is.
  `simplify`  it can be simpler; the finding says how.
  `remove`    it is not needed.
  `done`      a simplify or remove suggestion that has been applied.
  `moved`     the code was only relocated, not changed. Find such code with
              `git diff -M --color-moved` (https://git-scm.com/docs/git-diff).

Evidence values (how the agent knows):
  `ran`       it ran something that shows it.
  `read`      it read the code and inferred it.
  `opinion`   a judgement.

You decide on a finding, or on a proposal in a thread, with `Py` (accept) and
`Pd` (decline). `P0` takes a decision back while the agent has not been told.
The decision is sent at once. What the agent does with it:

  - an accepted proposal: it applies it, then reports in the thread with
    `answer` and `done`;
  - an accepted `simplify` or `remove` finding: it applies it and patches the
    finding to `done`;
  - a declined proposal or a rejected finding: it leaves the code as it is.

Decisions use the values `accept` and `reject`; the levels of `explain` are
`simpler` and `deeper`.

==============================================================================
10. STAGING AND REJECT                                     *walkthrough-stage*

Staging is step one of approval. `stage` (`Ps`) stages exactly the lines of the
current commit in the file of the current entry (in the compact view: the entry
under the cursor); `stage all` (`PS`) does it in every file of the commit. It
calls gitsigns' `stage_hunk` with a line range, one range after the other, and
reads the result back from git, so a file that also holds lines of other
commits only gets this commit's lines
(https://git-scm.com/docs/git-add).

It refuses when gitsigns is missing, when the code window shows another file,
when the buffer has unsaved changes, or when a range of the commit is stale
(|walkthrough-stale|). It reports how many lines were staged and what could
not be staged. An untracked file is registered with `git add -N` first, which
stages no content and only makes git see the file. `stage all` asks first
("N of M entries were not shown yet. Stage ... anyway?", the default is no)
when entries were not shown yet. The lines you staged turn into muted lines
with a ✓, and the panel counts them (`staged x/y`).

*walkthrough-reject*
`reject` (`Px`) is the counterpart: it discards the unstaged lines of the
commit in the current file, after asking ("Discard N unstaged lines of commit
..."; the default answer cancels). Staged lines stay. gitsigns restores the
lines from the index and the buffer is written. It refuses for an entry
without `hunks`, for a file that is new to git (there is nothing to restore it
to), and while a range is stale. It cannot be undone.

==============================================================================
11. THE COMMIT DIALOG                                     *walkthrough-commit*

Approval has two steps. Step one is staging. Step two is `:Walkthrough commit`
(`PC`), which does three things at once:

  1. It starts the project's check in the background, on exactly what is
     staged (|walkthrough-commit-check|). The editor is not blocked.
  2. It asks the agent for a message through the sender: the commit, the
     staged files (`git diff --cached --stat`), the rules "Conventional
     Commits. One line. Add further lines only when the change is really
     complex. Never add a Co-authored-by line." and the patch to answer with,
     `{ "commit_message": "<message>", "group": "<commit>" }`
     (|walkthrough-patch|). If sending fails, the dialog says so.
  3. It opens a centered float with an editable buffer laid out like git's own
     message file: the message on top (empty at first, or the message stored
     for the commit), then lines that start with `#` and are never part of
     the message:

>
    feat(net): share the LAN constants

    # Commit: Share the LAN constants
    # Staged:
    #   M  net.nix
    # check: running…
    # agent: message received
    #
    # Lines that start with # are not part of the message. <CR> commits, q cancels.
<

The `#` lines name the commit, the staged files, the state of the check
(`check: running…`, `check: passed`, `check: FAILED` followed by the last 15
lines of its output, `check: none defined`), whether the agent's message is
awaited, and a warning for every staged file that is not an entry of the commit
(`staged but not part of this commit in the map: {file}`).

It refuses, with a notification and no side effect, when there is no review,
when only threads on other files are loaded, when nothing is staged, or when a
commit dialog is open for the repository already.

The agent's message is put into the dialog when you have typed nothing in the
message area. If you have, it is not overwritten: a `#` line says that a
proposal arrived, and <C-r> in Normal mode replaces the text with it. The `#`
lines are written again in place when the check finishes; what you typed and
the cursor stay. A message that arrives before the dialog opens is stored on its
commit (saved with it) and shown when the dialog opens. Keys in Normal mode:

  <CR>      commit. `:w` does the same.
  q  <Esc>  cancel. Nothing changes: what is staged stays staged, and the
            stored message is kept for the next time. Closing the dialog in
            any way stops a check that is still running.
  <C-r>     take the proposal that arrived while you were typing.

To commit, the message is the buffer without its `#` lines, trimmed. An empty
message is refused. Every line that starts with `Co-authored-by:` (any letter
case) is removed, and you are told. If the check failed ("The check failed.")
or has not finished ("The check has not finished."), |confirm()| asks "Commit
anyway?" (the default is no): a failing or unfinished check is shown but does
not block. Then `git commit -F -` runs in the repository root with the message
on its standard input, hooks enabled (never `--no-verify`). If git fails, the
first line of its error is shown and the dialog stays open. On success the
dialog closes, a notification gives the short hash and the subject, and the
commit is deleted from memory and from the saved state, with its threads. The
next commit of the map is shown in its view. When none is left the panel closes
and the code window stays on the file it shows; `Other files` stays loaded.

==============================================================================
12. THE COMMIT CHECK                                *walkthrough-commit-check*

`skills/walkthrough/commit-check.sh` tests what a commit will contain.
`:Walkthrough commit` runs it in the background. It lists the staged and the
not staged files, copies exactly the index into a temporary directory
(`git checkout-index`, https://git-scm.com/docs/git-checkout-index) and runs a
check there. Your working tree is not used or changed. The check is, first
match wins:

  1. the command in `$WALKTHROUGH_CHECK` (run with `sh -c`).
  2. an executable file `.walkthrough/check` in the index.
  3. if `flake.nix` exists: build every host of `nixosConfigurations`. This is
     a Nix example. `commit-check.sh host ...` builds only those hosts.
  4. otherwise it prints "no check defined" and exits 0.

Checks 1 and 2 run with the checkout as working directory. If the check
fails, it is run again on HEAD. That tells a new failure ("this commit breaks
it") from an old one ("already broken"). The script exits 1 when nothing is
staged or the check fails.

To define a check for your project, write `.walkthrough/check` as an
executable script that exits non-zero on failure, and stage it:

>sh
    #!/bin/sh
    npm test
<

==============================================================================
13. PLAN REVIEW                                             *walkthrough-plan*

The agent proposes a plan before it edits, and waits for you. This opens the
plan in Neovim, where you annotate it and then approve it or send it back.
Claude Code is supported first; the hook is the only part specific to it.

How it works: Claude Code runs a `PermissionRequest` hook for `ExitPlanMode`
(https://code.claude.com/docs/en/hooks) when the agent wants to leave plan
mode, and waits for the hook. The hook script
`skills/walkthrough/hooks/plan-review.sh` finds the Neovim socket (as
`tour.sh` does), calls `plan({path})` with the hook input, then calls
`plan_result({id})` about once a second. When Neovim cannot do the review (no
Neovim, several without `$WALKTHROUGH_NVIM`, no plugin, an error) the script
prints nothing and Claude Code shows its normal permission prompt. So does
closing Neovim while the hook waits.

Settings, in `~/.claude/settings.json` (the timeout is in seconds; the hook
waits for you):

>json
    { "hooks": { "PermissionRequest": [ { "matcher": "ExitPlanMode", "hooks": [ {
      "type": "command",
      "command": "~/.claude/skills/walkthrough/hooks/plan-review.sh",
      "timeout": 86400
    } ] } ] } }
<

The plan opens in a new tab as a read-only markdown file,
`<state_dir>/plans/<id>.md`, where the id is the session id and a counter.
Other tabs and their windows are not touched. A notification says that a plan
waits, and the tab's winbar names the keys. In that buffer:

  A                 approve (`:Walkthrough plan approve`)
  F                 send feedback (`:Walkthrough plan feedback`)
  `ask`, `change`   annotate lines as everywhere (|walkthrough-mappings|).
                    Here both kinds are collected, because the agent is
                    waiting in its hook. `send` is refused there and points to
                    feedback. `decide` and `explain` do nothing in a plan.

The default keys `PA` and `PF` do the same from any buffer when one plan waits.

Feedback is one message: every annotation not delivered yet, numbered, with
its kind (question or change request), the plan lines it is about (quoted, at
most 5), and your text. It ends with what the agent should do: answer each
question, revise the plan for each change request, and reply to every item
with a patch `{ "thread": "<id>", "answer": "..." }` (|walkthrough-patch|)
before it presents the plan again. With no annotation, it asks "What should
change?" and sends your answer; an empty answer cancels. The tab stays open and
its winbar says "feedback sent; waiting for the revised plan". The agent's
replies are drawn under your lines like any answer.

When the agent presents the revised plan, the hook calls `plan()` again for
the same session: the new text replaces the old one in the same tab (opened
again when you closed it), and your threads stay and follow their lines.
Threads on lines that were rewritten are stale, as for code
(|walkthrough-stale|). Approving closes the tab and deletes the plan, its
file and its saved state; annotations still open are dropped and the
notification says how many.

A plan is a commit flagged `plan` with one entry, the plan file, and nothing
else sees it: it is in no map, and `review`, `stage`, `commit`, `send` and
`inbox` ignore it. `close()` leaves it (it does not approve or deny). It is
saved with the review state, so a restart keeps your threads: the next plan of
the same session continues the saved review, and `:Walkthrough plan` brings it
back. See `status()` (|walkthrough-status|) for `plan`.

==============================================================================
14. EXISTING CODE, RESTORE, CLOSE                          *walkthrough-other*

You can write on any file, not only on the files of a review. `ask` and
`change` (and a reply) work in the current window on the current buffer, in a
repository or not, without switching windows, buffers or the shown entry. The
buffer must be a saved file. Where the thread goes:

  - the file is an entry of a loaded commit of the same repository: that entry
    (the active commit's first, else the first commit that lists the file);
  - the file is in no loaded commit: an entry of `Other files`, made on
    demand and flagged `extra` in the saved state. The map lists it last, under
    that heading, each entry with its path and no staged numbers;
  - nothing is loaded for the repository: a session starts by itself. The
    repository's saved commits are brought back first (silently), then the
    rule above applies. No panel opens and no window changes. A file outside a
    repository uses its directory as the repository.

Thread ids are unique across all commits of a repository, so an agent patch
`{ "thread": "t3", ... }` needs no `step`. `send`, `inbox()` and `status()`
cover all commits of the repository; each item names its commit's subject, or
`Other files`.

Threads are drawn in every window whose buffer is a file with threads, with
the same look as in the code window, and again after a save, an outside edit,
an answer, a decision or a deletion. The keys `]n` and `[n` and the actions
`thread`, `decide`, `explain` and `thread-delete` act on the file in the
current window. A buffer with unsaved changes keeps the marks it has.

When a normal file is shown for the first time in a repository with nothing
loaded, the repository's saved state comes back by itself (once per repository
and Neovim session; no panel, no window or buffer change), so the threads are
there after a restart. That needs the plugin loaded, so call `setup()` in your
configuration. `:Walkthrough close` (`Pq`) ends the session: it deletes
`Other files` from the saved state (the commits of a change stay), and the
repository is not restored by itself again. When a review starts (`review` or
a map from the agent) and a file of `Other files` is an entry of it, its
threads move to that entry and the old one goes away. Deleting the last thread
of an `Other files` entry removes the entry.

==============================================================================
15. PERSISTENCE                                      *walkthrough-persistence*

Each change to the review saves all loaded commits of the active repository to
one JSON file. Changes are: a map or patch from the agent, a review, moving to
an entry or commit, a thread, a decision, a send, an explain request and a
reject. The file is:

  {state_dir}/{sha256 of the repository root}.json

`state_dir` defaults to `stdpath('state') .. '/walkthrough'` (|stdpath()|). The
file is written beside itself and renamed, so a crash leaves no half file. A
failure to save is reported once and otherwise ignored. It has the format
version 2. A file of version 1 (entries with `panel` and `check`, and
`comments`) is read too: those fields are dropped, the comments become threads
(a question stays one, an issue or suggestion becomes a change request, the
answer an agent message), the rest is kept, and the next save writes version 2.
The step field `total` of older files is dropped as well.

  `:Walkthrough resume`   reads the file of the repository of the working
                          directory (else of the current file), brings the
                          commits back, and shows the active one where you left
                          it. Entries follow the edits made meanwhile. An
                          entry whose file is gone, or that no longer
                          validates, is dropped. So is a commit whose entries
                          all have `diff` true and whose files have no
                          uncommitted change any more (it was committed).
                          Without a saved review it answers "nothing to
                          resume".
  `:Walkthrough discard`  deletes the file and clears the screen.
  `:Walkthrough close`    ends the session: clears the screen and forgets the
                          loaded commits. The commits of a change stay in the
                          file, so `resume` brings a review back; `Other files`
                          is deleted from it (a file left without commits is
                          deleted).

When nothing is loaded for a repository and it has a saved review, the next
`load`, `ask` or `change` brings the saved commits back first (silently), so
sending a commit after a restart does not wipe the others. The thread counter
is kept per repository in the file, so ids are not reused after a restart.

==============================================================================
16. SENDERS                                              *walkthrough-senders*

Everything for the agent (a question, `send`, a decision, `explain`, the commit
message request, the request for the map) is built as a message and handed to
the sender chosen by `sender`. The message is a table:

  `text`     markdown for the agent.
  `refs`     a list of `{ file, from, to }`: the code the message is about.
  `submit`   whether the agent should start on it without further input
             (the option `submit`, true by default).
  `prefill`  optional text for the prompt, typed but not submitted.

The senders:

  "claudecode"  needs https://github.com/coder/claudecode.nvim (the command
                `:ClaudeCodeAdd`). It writes the text to a temporary file and
                attaches it and the code references. With `submit` it then
                types one line that points at the file into the Claude prompt
                and submits it; the focus stays where it is. Without `submit`
                it focuses the Claude terminal and types that line (the
                `prefill`, if there is one) without submitting it.
  "terminal"    pastes the text into the terminal buffer of a running agent as
                one bracketed paste. With `submit` a carriage return follows
                and you stay where you are; without it nothing is submitted
                and you are moved to that window. The terminal is found by
                `terminal_pattern`. The text is plain, with the references as
                `path:from-to` lines.
  "clipboard"   copies the plain text to the `+` register (to the unnamed
                register when Neovim has no clipboard provider).
  a function    `sender = function(msg) ... end`. It receives the message
                table, `msg.submit` included. If it raises, the items are not
                marked as sent: a thread stays a draft and goes out with the
                next `send`.
  "auto"        the default. "claudecode" when its command exists, else
                "terminal" when an agent terminal is found, else "clipboard".
                `:checkhealth walkthrough` shows the choice.

`terminal_pattern` is matched against the buffer name and the terminal title,
ignoring case. A function receives `(name, title, buf)` and returns a boolean.
Only terminal buffers with a running job count.

A message to the agent starts with `Walkthrough:`, lists its items, and gives
each an `Expected:` line that says what to do and with which patch. Example:

>
    Walkthrough: feedback from the user on commit "Share the LAN constants"
    (1 item). Answer by patching the map in place.

    1. Question t1 at net.nix:10-12, step 1
       Code:
         lan = { ... };
       User: why a set here?
       Expected: Answer it without changing any code, with a patch:
       { "thread": "t1", "answer": "..." }
<

An agent that cannot be pushed to can pull instead: `tour.sh --inbox`
(|walkthrough-inbox|).

==============================================================================
17. THE PROTOCOL                                          *walkthrough-format*

This is the short form. The complete one, with examples, is
`skills/walkthrough/references/format.md`. The JSON names are older than the
words of the product and stay: a commit of the map is an object with a `group`
and `steps`, an entry is a step, a finding is a note.

A file given to load() holds one JSON object: a commit (it has `steps`) or one
entry (it is appended to the active commit; without one it starts a commit
without a subject). Everything is checked before anything changes. A problem
comes back as one line, for example `error: step 2, note 1: "line" is
missing`. A failed load changes nothing and leaves the screen as it was. An
unknown field is an error, so a typo is reported.

>json
    { "group": "Share the LAN constants",
      "steps": [{
        "file": "/home/me/project/net.nix",
        "title": "the constants move into one set",
        "from": 10, "to": 20,
        "hunks": [{ "from": 10, "to": 20 },
                  { "from": 41, "to": 41, "group": "Use the constants" }],
        "notes": [{ "line": 12, "text": "few words", "verdict": "simplify",
                    "evidence": "read", "detail": "the explanation" }]
      }] }
<

Text fields (`text`, `detail`) take a string, or a list of strings that are
joined as lines. Line numbers are 1-based and inclusive, and mean the file as
it is on disk now. The agent sends the commits of the map one per call, in
order; the map lists them in the order they were sent.

Commit fields

  `group`   string. The commit's subject, and the default `group` of its
            entries. The commit being reviewed is this one.
  `steps`   list of entries, not empty.
  `start`   integer, 1 or more. The entry to open first. Default 1. It is
            limited to the number of entries. Other fields at the top level
            are ignored.

Sending a commit with the `group` of a loaded one replaces it and keeps what
you did (seen entries and threads of entries with the same `file` and `title`,
depth, view, a stored commit message). A commit
with a `group` replaces the local review of its repository and takes its
threads over by file; the request for the map ends (|walkthrough-request|).

Entry fields (all optional except `file`)

  `file`    string, required. Path of an existing, readable file. Use an
            absolute path: a relative one is read from Neovim's working
            directory.
  `title`   string. One sentence that says what changed in this file. The map
            shows it under the file name.
  `group`   string. Default: the commit's `group`.
  `from`    integer, 1 or more. First line of the focus.
  `to`      integer, `from` or more. Last line of the focus. Needs `from`.
  `diff`    `true`, `false` or a git ref (a string). `true` shows everything
            uncommitted (the file against HEAD), with staged lines muted. A
            ref gives a plain diff against that ref
            (https://git-scm.com/docs/gitrevisions) with no staged marks. An
            entry that has `hunks` and no `diff` gets `true`. An entry with
            neither has no overlay.
  `hunks`   list of hunks: the changed lines of the file, by commit.
  `notes`   list of notes (the findings).

The fields `panel`, `check` and `total` of earlier versions are gone. Sending
them is an error like any unknown field.

Hunk fields

  `from`    integer, 1 or more, required. First line of the range.
  `to`      integer, `from` or more. Last line. Default `from`.
  `group`   string. Default: the entry's group.

Ranges of one entry must not overlap. A change in a range of the entry's
commit is drawn in full and is what `stage` stages. A change in a range of
another commit is dimmed and labelled with that commit. A change in no range is
flagged "not in any commit". A deleted line has no line of its own: it counts as
being on the line where it is shown (|walkthrough-limitations|).

Note fields

  `line`      integer, 1 or more, required, and not past the end of the file.
  `text`      text. A few words, drawn under the line.
  `detail`    text. A longer explanation. The code window shows it under
              `text`, wrapped, at most 6 lines.
  `verdict`   one of the verdicts (|walkthrough-verdicts|).
  `evidence`  one of the evidence values (|walkthrough-verdicts|).

Notes are numbered 1, 2, ... in list order. The number appears in the badge and
in the tag `[n]` in front of the text. A number is never reused and never
changed by a patch, except when a patch replaces the whole `notes` list.

Some fields are written only by the plugin and are not valid in an agent's
JSON: `stale`, `seen`, `threads`, `decision`, and the note's `n`. A patch cannot
set them either.

==============================================================================
18. PATCHES                                                *walkthrough-patch*

patch() changes what is loaded in place. Resend only what changed. The file
holds one patch (an object) or a list of patches. `step` is the entry number
(1-based) in the active commit. It defaults to the current entry.

>json
    [{ "step": 2, "from": 12, "to": 15, "title": "new sentence" },
     { "step": 2, "unset": ["title", "to"] },
     { "step": 2, "note": 3, "verdict": "done", "detail": "Applied: ..." },
     { "step": 2, "note": 4, "line": 30, "text": "a new finding" },
     { "step": 2, "note": 1, "remove": true },
     { "step": 2, "note": 3, "unset": ["detail"] },
     { "thread": "t1", "answer": "Because ..." },
     { "thread": "t2", "answer": "I would ...", "proposal": true },
     { "thread": "t2", "answer": "Applied: ...", "done": true },
     { "thread": "t3", "answer": "The same, simpler: ...", "replace": true },
     { "commit_message": "feat(net): share the LAN constants", "group": "A" }]
<

The forms:

  Entry fields    any entry field of |walkthrough-format|: `file`, `title`,
                  `from`, `to`, `diff`, `hunks`, `notes`, `group`. A list field
                  (`hunks`, `notes`) is replaced as a whole. Replacing `notes`
                  numbers the new notes from 1.
  `unset`         a list of field names to remove. In an entry patch they are
                  entry fields, in a note patch note fields. It exists because
                  JSON `null` is dropped when the file is read.
  Note patch      has `note`, the note's number. It changes the fields it
                  names. Giving `line` says where the note is now, and clears
                  its "code changed" mark.
  New note        `note` is the next free number, and `line` is given. The next
                  free number is one above the highest number ever used in the
                  entry, also after removals. A wrong number is answered with
                  the right one.
  `remove`        `true` together with `note` drops the note.
  Thread patch    has `thread`, an id such as "t1" (|walkthrough-inbox|); ids
                  are unique in the repository. Allowed keys: `thread`, `step`
                  (limits the search to that entry), `answer` (text, or a list
                  of lines), `proposal`, `replace` and `done` (booleans). It
                  cannot be combined with `note`. `answer` appends a message of
                  the agent and the state becomes "answered"; with `proposal`
                  the message is a proposal and the state becomes "proposed";
                  with `replace` it replaces the last message of the agent
                  instead and the state stays; with `done` (and `answer` if
                  given) the state becomes "done". `proposal` and `replace`
                  need `answer`, `replace` cannot go with the other two, and
                  `done` cannot go with `proposal`. The agent may do nothing
                  else: creating and deleting threads, writing for the user and
                  every other state are the user's.
  Commit message  has `commit_message` (a string, or a list of strings that are
                  joined as lines) and optionally `group`, the commit it is
                  for (default: the active commit). It answers the request that
                  `commit` sends (|walkthrough-commit|). The message is kept on
                  that commit and shown in the open commit dialog. It is
                  rejected when no commit of that `group` is loaded, and cannot
                  be combined with other keys.

The whole list is applied to copies of the entries. Every entry it touched is
validated again. If any item or the result is invalid, nothing changes (`error:
patch 2: ...`). Before the patch, the numbers in the entries it names are moved
to follow edits made to their files, so the agent's numbers mean the lines on
disk now. A patch that changes `file`, `from` or `to` of the current entry
opens it again. Any other patch redraws it without moving the cursor. An answer
in a thread never brings the shown entry back to the code window.

==============================================================================
19. STATUS()                                              *walkthrough-status*

status() returns a JSON string, or `{"step":0}` when nothing is open. With
commits loaded but no entry shown (only `Other files`) it returns `{"step":0}`
with `threads` and `groups`. It brings every entry up to date first. Fields:

  `step`    number of the current entry (1-based).
  `total`   number of entries in the active commit.
  `title`   sentence of the current entry, when it has one.
  `file`    file of the current entry.
  `group`   commit of the current entry.
  `seen`    how many entries of the active commit were shown to you.
  `view`    "compact" or "file": the view on screen (|walkthrough-views|).
  `groups`  one item per loaded commit: `group` (the subject; `Other files`
            for threads on files no review lists, which also has `extra`
            true), `steps` (count), `seen` and `current` (true for the active
            one).
  `stale`   absent when nothing is stale. Otherwise a list of what edits
            invalidated and the agent should patch:
            `{ "step", "kind": "note", "note", "line" }`,
            `{ "step", "kind": "hunk", "from", "to", "group" }`, or
            `{ "step", "kind": "missing" }` (the entry's file can no longer be
            read).
  `depth`   "simpler" or "deeper" after `explain`: the level you asked for.
            Absent otherwise. The agent writes later answers at that level.
  `commit`  present while a commit dialog is open (|walkthrough-commit|):
            `{ "group", "check", "message" }`. `check` is "running", "passed",
            "failed" or "none" (no check defined). `message` is true when the
            message area holds text.
  `threads` absent when there is no thread to count. Otherwise `{ "draft",
            "waiting", "answered", "proposed" }`, the number of threads of the
            repository (all its commits) in each state.
  `plan`    absent unless a plan is under review (|walkthrough-plan|): `{ "id",
            "state", "threads" }`. `state` is "pending" (waiting for you) or
            "feedback-sent". A plan is no item of `groups` and its threads are
            not in `threads`.
  `map`     "requested" while the request for the map (|walkthrough-request|)
            has not been answered by a map. Absent otherwise.

`seen` is the only evidence of what you looked at.

==============================================================================
20. INBOX()                                                *walkthrough-inbox*

inbox() is the pull side of `:Walkthrough send`, for an agent that has no
editor integration. It returns JSON for the repository:
`{ "group": "...", "items": [ ... ] }`, or `{"items":[]}` when nothing is
open. The items are what was not delivered yet, and each counts as delivered
afterwards (its thread is "waiting"), so a second call lists only what is new.
`inbox(true)` also lists the threads that wait for an answer. It covers all
commits of the repository, the commits of a change first and `Other files`
last; each item has `group`, the name of its commit (`Other files` for threads
on files no review lists, where `step` is the entry's number there). Items come
in entry order, threads sorted by line. The item kinds (`kind`):

  `question`  a thread of yours: `id` ("t1"), `group`, `step`, `file`, `from`,
              `to`, `state`, `messages` (a list of `{ "by": "user" or "agent",
              "text", "proposal" }`), `new` (the 1-based index of the first
              message the agent has not seen) and `stale`.
  `change`    the same fields, for a change request.
  `decision`  your decision. On a proposal: `id`, `group`, `step`, `file`,
              `from`, `to`, `decision` ("accept" or "reject"), `state`, `text`
              (the proposal). On a finding: `group`, `step`, `note` (the
              number), `verdict`, `decision`, `file`, `line`, `text`.
  `commit`    `group`, `stat` (the text of `git diff --cached --stat`): you
              asked for a commit message (|walkthrough-commit|). Listed until a
              message arrived or the dialog was closed; reading the inbox does
              not deliver it. Answer with a patch `{ "commit_message": "...",
              "group": "..." }`.
  `map`       `root`, `base`, `files`: you asked for the map
              (|walkthrough-request|). Listed until a map arrives, the session
              is closed or the review is discarded; reading does not deliver
              it. It has no `group`.

What is expected: a `question` gets a thread patch with `answer`. A `change`
gets a proposal (`answer` with `proposal`) and no edit of the code. An accepted
proposal is applied, then reported with `answer` and `done`; a declined one is
left alone. An accepted `simplify` or `remove` finding is applied and patched
to `done`; a rejected decision is left alone. A `commit` gets the message. A
`map` gets the commits of the map.

21. POSITIONS AND STALE                                    *walkthrough-stale*

An entry stores line numbers, and the file keeps changing (you edit it, the
agent edits it). So each entry also keeps a copy of the file as the numbers
last referred to it. When an entry is drawn, patched, staged or reported by
status(), the file on disk is compared with that copy (|vim.diff()|, ignoring
changes in whitespace) and every number is moved through the difference. Lines
inserted above a thread move it down. Nothing is asked of the agent.

A number is marked `stale` when moving it is a guess:

  finding   its line was rewritten or deleted. It is drawn with "(code
            changed)".
  range     an edit reaches over an edge of a `hunks` range. The ends are a
            guess, the lines are labelled "stale range", and `stage` and
            `reject` refuse until the agent patches the `hunks`. Lines inserted
            directly before or after a range, or inside it, are no conflict:
            the range moves or grows.
  thread    the code it was written on was rewritten (shown as "(code
            changed)").

A range whose lines were all deleted collapses onto the line where the deletion
is shown. If another range owns that line, the collapsed range is dropped. The
focus (`from`, `to`) is never stale; it follows as well as it can.

status() lists stale findings and ranges under `stale` (not threads). After an
edit the agent runs status() and patches what is listed. A patch that gives a
finding a `line`, or replaces `hunks`, ends the stale state.

The numbers follow the file on disk. While the code buffer has unsaved
changes, the diff overlay is paused (git sees only the saved file) and the
panel's bar says "unsaved changes: save to refresh". Writing a thread, staging
and reject need the file saved. The overlay redraws by itself when the file is
written, reloaded after an outside edit, or staged.

24. SNAPSHOTS (NOT IN THE WORKFLOW)                  *walkthrough-incremental*

A snapshot records the working tree as a commit object under
`refs/walkthrough/{name}`. An entry with `"diff": "refs/walkthrough/reviewed"`
then shows only what changed after that point. The workflow does not use it,
but the command stays.

  snapshot({name})  or  `:Walkthrough reviewed [name]`  or
  `tour.sh --snapshot [name]`

records the working tree (tracked and untracked files, not ignored ones). The
default name is "reviewed". A name starts with a letter or digit and contains
letters, digits, ".", "_" and "-". It must not contain "..", and must not end
with "." or ".lock". The call returns the commit id, or `error: ...`. The
repository is the active commit's, else the one of the working directory.

Your index, your working tree, HEAD and your branches are not touched. Inside,
the plugin does this (https://git-scm.com/docs/git-read-tree,
https://git-scm.com/docs/git-add, https://git-scm.com/docs/git-write-tree,
https://git-scm.com/docs/git-commit-tree,
https://git-scm.com/docs/git-update-ref): it seeds a temporary index file
(`GIT_INDEX_FILE`) from HEAD when HEAD exists, runs `git add -A` into it, makes
the tree with `git write-tree`, makes a commit with `git commit-tree` (parent
HEAD when it exists), and stores it with `git update-ref`. A repository without
commits works. If git has no author identity configured, the commit is made as
"walkthrough".

An entry against a ref is a plain diff against it: only lines changed after
the snapshot are marked, also for a file that is untracked in the working tree.
It has no staged/unstaged split: no muted lines, no ✓, and its lines are not
counted in `staged x/y`. Staging still works with `hunks`.

A snapshot is an ordinary ref and the plugin never removes it. Remove one with
`git update-ref -d refs/walkthrough/{name}`. List them with
`git for-each-ref refs/walkthrough/`.

25. LIMITATIONS                                      *walkthrough-limitations*

- A deleted line cannot have its own commit. `hunks` address lines of the new
  file, and a deleted line has none, so it counts as being on the line where
  it is shown: a deletion between two lines is shown below the line before the
  gap (above line 1 when it is at the top). Example: commit A changes line 4
  and commit B deletes the line below it. Git reports one hunk. The overlay
  shows both as A's, gives no "mixed hunk" warning, and `stage` for A stages
  B's deletion too. The commit check is the safety net. An agent should say so
  in a note when it happens.
- Neovim may not show virtual lines above line 1 (`virt_lines_above`) unless
  the window is scrolled with filler lines. A deletion at the top of a file
  can then be invisible in the file view. Not checked here.
- When a hunk replaces n old lines with m new lines and the new lines are
  split between commits, gitsigns pairs old and new lines by position when
  staging. That is a heuristic.
- A deleted file cannot be an entry (`file` must be readable). Write the old
  version to a temporary file, for example `git show HEAD:path > /tmp/x`, and
  use that.
- A file that is new to git cannot be rejected: git has nothing to restore it
  to.
- Positions follow the file on disk, so an edit that is not saved yet is not
  seen (|walkthrough-stale|). Edits move numbers by a diff, which can guess
  wrong when a large block is rewritten. Such findings and ranges are marked
  stale.
- Staging and reject need gitsigns.nvim, and for the file view the entry's file
  in the code window.
- Moved code is detected by the agent only. The plugin draws a moved block like
  any other change.
- A snapshot is not cleaned up automatically. It keeps the objects of the files
  it recorded, so a large untracked tree takes space until `git gc`.
- The panel and the overlay belong to one tab. A review left open in another
  tab does not draw there.
- A plan has no proposals or findings: `decide` and `explain` do nothing there.
